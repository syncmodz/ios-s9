# Como construir o kernel 7195 (iOS 14.3) nesta máquina

**Verificado em 2026-11-16.** Este é o comando que funciona, e a razão de cada
parte dele. Antes disso, três sessões procuraram a árvore errada.

## A árvore certa

```
/Users/ios/s9work/xnu7195-local
```

Não é `work/xnu` (essa é **8796**), nem `work/xnu7195` (essa é a 7195 *pristine*,
sem os arquivos sweet), nem a cópia em `/Volumes/Linux/.../S9-iOS14-Development`
(que nunca teve `BUILD/`). `xnu7195-local` é a única árvore 7195 completa e já
compilada, e o kernel que roda no aparelho diz literalmente
`ios:xnu7195-local/BUILD/obj/DEVELOPMENT_ARM64_SWEET`.

Ela não é um repositório git. **Faça backup antes de editar** — não há `git diff`
para desfazer.

## O comando (o que de fato compilou)

A árvore **não builda com o SDK do Xcode**. Precisa do SDK de kernel já montado
em `/Users/ios/s9build/hakios/xnu-deps` — o harness do projeto hakios, que
resolve dois problemas de uma vez: o SDK `iPhoneOS16.5.xnu.sdk` traz headers que
o 7195 inclui e o Xcode não tem (`os/firehose_buffer_private.h`), e o **shim de
`iig`** (`xnu-deps/host/bin/iig`) copia headers pré-gerados do SDK do macOS 13.3
em vez de rodar o gerador do Xcode 26 — que era o que emitia `kernelContent`.

```sh
cd /Users/ios/s9work/xnu7195-local
export XNUDEPS=/Users/ios/s9build/hakios/xnu-deps
export XNU_SDK_VERSION=16.5
export XNU_SDK_PATH=$XNUDEPS/sdk/iPhoneOS16.5.xnu.sdk
export XNU_PLATFORM_PATH=$XNUDEPS/sdk/Platforms/iPhoneOS.platform
export PATH=$XNUDEPS/host/bin:$PATH      # xnu-clang, xnu-clang++, iig, xcrun

make SDKVERSION=16.5 SDKROOT=iphoneos \
     ARCH_CONFIGS=ARM64 MACHINE_CONFIGS=SWEET KERNEL_CONFIGS=DEVELOPMENT \
     ARCH_STRING_FOR_CURRENT_MACHINE_CONFIG=arm64 \
     BUILD_WERROR=0 BUILD_LTO=0 DO_CTFMERGE=0 \
     HOST_FLEX=flex HOST_BISON=bison HOST_GM4=m4 \
     CC=xnu-clang CXX=xnu-clang++ LOGCOLORS=n
```

Saída: `BUILD/obj/DEVELOPMENT_ARM64_SWEET/mach.development.sweet`.

**Verificado:** o kernel foi regerado —
`Darwin Kernel Version 20.2.0: seg 16 nov 2026 19:14:36 -03; ios:xnu7195-local/...`,
12 MB.

### `XNU_SDK_PATH` e `SDKVERSION` têm de ser exportados

Sem `XNU_SDK_PATH` o `xcrun` do harness falha em silêncio (`XNU_SDK_PATH not set`)
e o include de `os/firehose_buffer_private.h` não resolve. Sem `SDKVERSION=16.5`
o `-mmacosx-version-min=` sai vazio e **37 arquivos** falham com
"missing version number".

### O único erro que sobra é cosmético

```
env: python: No such file or directory   (cvalue.py, lazytarget.py, ...)
```

O alvo `config_all` do `lldbmacros` chama `python`, que o macOS moderno não tem
(só `python3`). Acontece **depois** do kernel estar linkado, e o
`mach.development.sweet` de 19:14:36 prova. Um `python -> python3` no PATH
silencia; não bloqueia nada.

### `MACHINE_CONFIGS`, no plural

Foi o erro que mais custou tempo. `MACHINE_CONFIG=SWEET` (singular) é **ignorado
em silêncio**: o build cai no default `T7000` e produz
`BUILD/obj/DEVELOPMENT_ARM64_T7000/`. Nesse diretório o `iig` do Xcode gera
código com `IORPC.kernelContent`, que a 7195 não tem — 35 erros de compilação
que parecem um problema de fonte e são, na verdade, o build indo para a
configuração errada. Verificado com `make -n ... | grep -o DEVELOPMENT_ARM64.*`:
singular dá `T7000`, plural dá `SWEET`.

### `BUILD_WERROR=0`

O Xcode 26 é mais estrito que o compilador de 2024 com que a árvore foi feita.
`-Weverything -Werror` transforma avisos inofensivos em erro,
`-Wreserved-identifier` à frente (`__int8_t` em `bsd/arm/_types.h`). Desligar o
`-Werror` é mais honesto que desligar avisos um a um: o código não mudou, o
compilador ficou mais exigente. (`makedefs/MakeInc.def:141`)

### O diretório `EXPORT_HDRS/libsa`

O build emite `-I.../BUILD/obj/EXPORT_HDRS/libsa` mas nada o cria, e
`-Wmissing-include-dirs` (também sob `-Werror`) transforma isso em erro. Um
`mkdir -p` resolve. Se o build falhar só com "no such include directory", é isto.

### O `availability.pl` (só no caminho do SDK do Xcode)

Com `SDKROOT=iphoneos` e o SDK do harness isto não aparece. Só existe no caminho
`SDKROOT=macosx PLATFORM=MacOSX`, que **não** é o que compila esta árvore. Fica
registrado porque eu criei um stand-in dentro de
`/Applications/Xcode.app/.../MacOSX.sdk/usr/local/libexec/availability.pl`
enquanto tentava aquele caminho: **isso altera a instalação do Xcode** e some na
próxima atualização. Pode ser removido sem prejuízo.

## O que foi corrigido por mim e não deve ser repetido

Ao montar uma árvore 7195 a partir do zero (`work/xnu7195`), copiei do 8796 o
`iokit/DriverKit/` inteiro. Três arquivos `.iig` são de 2023 e não existem na
7195 — `IOWorkGroup.iig`, `IOEventLink.iig`,
`IOServiceStateNotificationDispatchSource.iig` — e fazem o `iig` gerar
`kernelContent`, que a 7195 não tem. **Foram removidos** de `xnu7195-local`.
O conjunto correto é o de 14 arquivos, igual ao pristine.

Também escrevi dois stubs (`bsd/dev/sweet_bcb.c`, `sweet_wdt.c`) com endereços
MMIO inventados antes de descobrir que os arquivos reais estavam em
`xnu7195-local` desde o começo. Foram apagados. **Não invente endereço de
registrador**: os arquivos reais existem.

## Erros que restam e o que são

Depois de tudo acima sobram famílias pequenas, todas de API de versão diferente
entre 7195 (2020) e 8796 (2023):

| erro | onde | natureza |
| --- | --- | --- |
| `pmap_sign_user_ptr` não declarada | `pmap.h` | função existe na 8796, não na 7195 |
| `MANIPULATE_SIGNED_THREAD_STATE` | `thread_status.h` | macro da 8796 |
| `machine_thread.disable_user_jop` / `jop_pid` | `thread.h` | campo da 8796; `task` tem, `machine_thread` não |
| `static_assert` de layout de VA | `mach/arm/vm_param.h` | depende de `ARM_LARGE_MEMORY` e dos valores de DRAM |

Nenhum é fatal para produzir um kernel: o `mach.development.sweet` de 15 nov
existe e roda no aparelho. O que decide se o próximo build é utilizável é o
conjunto de erros que sobra depois do `-j1`, não a contagem em paralelo (a saída
paralela mistura linhas de várias compilações e é ilegível).
